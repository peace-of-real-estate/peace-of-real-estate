Part I

Product spec

What to build and why — rationale attached to each rule.

1 · Context

Goal & current state

Matching already works: buyers/sellers complete a quiz, and /buyer/matches & /seller/matches score agents via calculateFitScore. What's missing is everything after the list — choosing agents, the bilateral handshake, and monetization.

The product loop

  1. Client selects 1–3 agents from their matches and sends introduction requests.
  2. Each agent reviews an anonymous fit card (no contact info) and accepts or declines.
  3. On first acceptance, the client can pay $20 for a 6-month access window.
  4. Every acceptance during an active window becomes connected: full mutual contact exchange, delivered in-app and by email.

Design principles

A fresh build — the discarded alpha's four failures are now the design's four invariants:

Contact info never leaves the server pre-connection. Response shaping, not UI hiding — the alpha shipped agent email/phone to every client and locked it with CSS.
The $20 cannot be bypassed. Agents accept blind; before payment neither side has anything to take off-platform.
The lifecycle is complete. Every state is reachable and leavable — no ghosting agent can hold a client's slot forever.
Caps are enforced by the database. Constraints and transactions, not read-then-insert checks that lose races.

What exists on this branch today

  • Migrations run 0000–0006; there is no introductions table yet.
  • /buyer/introductions, /seller/introductions, and /agent/introductions routes exist but render a <Wip /> placeholder.
  • client-matches.tsx / match-list.tsx render matches with no introduction state.
  • userEntitlements is repurposed for the access window; email.server.ts has Resend wired up (password-reset template only); stripe is a dependency but no env vars, client, or webhook route exist yet.
Spec 2 Core mechanics
2.1 · State machine

Introduction lifecycle

One row in introductions per (client profile, agent) request, five statuses. Active = holds one of the client's 3 concurrent slots — scarcity keeps requests intentional and caps spam throughput by construction.

Active

pending, accepted — each holds one of the client's 3 slots. Also blocks a duplicate intro to the same agent via a partial unique index.

Terminal, retryable

declined, withdrawn — slot freed immediately; same agent re-requestable after the 30-day cooldown.

Terminal, permanent

connected — slot freed; contact info stays visible after the window lapses (the window gates new unlocks). Never re-requestable — you're already connected.

No auto-expiry — withdrawal instead

A pending intro never expires; the client may withdraw it after 24 hours. The agent gets a guaranteed day to respond, the client is never stuck behind a ghost, and the UI counts down until the withdraw button appears. No expired status.

2.2 · The core security property

Who sees what, when

Mutual reveal happens only after payment — acceptance alone reveals nothing, which closes the off-platform bypass. This matrix is the contract every server function must honor. Enforcement is server-side response shaping: loaders return Pick-derived view types per state (mirroring match.view.ts), never spread DB rows, so contact fields physically don't leave the server before connected. Client names are anonymized server-side ("Jane D.").

Status Client sees about agent Agent sees about client
pending Match card as on matches page (name, fit, profile) — agent identity is already public there. No email/phone. Anonymous fit card: "Jane D.", role, city/state, timeline, price range, property types, work-style answers when present, fit score. No email/phone/last name.
accepted Same + "accepted — unlock to connect" CTA. Still no contact info. Same anonymous card + "waiting for client to unlock" state. Still no contact info.
connected Full business card: name, email, phone, brokerage/identity fields. Full name + email.
declined / withdrawn Neutral "declined" (optionally softened category) / their own withdrawal. Row disappears from pending; history shows the anonymous card only.

The anonymous fit card

First name + last initial, role, city/state, timeline, price range, property types, work-style quiz answers when present, fit score — enough for a genuine accept/decline decision, zero identity or contact leakage. Essentials always show; quiz answers only when answered.

The contact exchange

On connected, the client gets the agent's full name, email, phone, and brokerage; the agent gets the client's full name and email. Deliberately no client phone field — email is enough, and collecting phones pre-need is friction plus liability.

2.3 · Monetization

Payment: the $20 access window

$20 buys a 6-month access window, scoped per role (buyer or seller profile); a returning user later simply pays again. The window is purchasable only after the first acceptance — paying at the moment of proven value keeps refund pressure near zero; there is no upfront purchase path. Stripe Checkout, mode: payment, fulfilled by a webhook route. The entitlement lives in userEntitlements with new keys intro_access_buyer / intro_access_seller, endsAt = now + 6 months.

Window semantics

  • While a window is active, an agent's accept transitions pending → connected directly — no second paywall moment.
  • Window expires with accepted intros outstanding → they stay accepted; buying a new window connects them.
  • Already-connected intros are untouched by expiry — connections are permanent.
  • Buyer and seller windows are fully independent purchases; a user with both profiles buys each separately.

Operational notes

  • No saved payment methods / auto-charge — plain Stripe Checkout per purchase; auto-charging on a later accept is a chargeback magnet.
  • Idempotency: fulfillment keyed on stripePaymentIntentId; re-delivered webhooks and already-connected intros are no-ops.
  • Webhook lag: the success redirect shows "processing payment…" and refetches for up to ~30s before telling the user to refresh.
  • Refunds: manual via Stripe dashboard for v1; entitlement revocation is a manual DB operation.
  • Config: dedicated STRIPE_INTRO_UNLOCK_PRICE_ID env var, plus the base STRIPE_SECRET_KEY / STRIPE_WEBHOOK_SECRET — env.server.ts has none of these today.
2.4 · Trust & safety

Anti-abuse guards

All guards run inside one transaction in the domain layer (src/lib/introductions/), serialized per client profile with a Postgres advisory lock so concurrent sends can't split-brain the caps. Every guard failure returns a distinct, user-readable error.

G1 Slot cap

Active intros (pending + accepted) after this send must be ≤ 3 per profile. Terminal states free the slot.

Why: throughput cap by construction — a determined spammer reaches ~3 new agents/day at most.

G2 Per-agent uniqueness + cooldown

Partial unique index blocks a second active-or-connected intro to the same agent. A decline or withdrawal starts a 30-day cooldown before that agent can be re-requested.

Why: protects individual agents from repeat pestering; kills "withdraw + immediately re-send" loops.

G3 Velocity cap

≤ 10 intros created per rolling 30 days per profile (counts every send, regardless of outcome).

Why: the backstop against slot-cycling via withdraw — genuine users never hit it; a slot-cycler hits it on day 3.

G4 Eligibility

Sender's profile must be past draft (essentials are enough — the quiz is deliberately skippable). Each target agent must be a non-disqualified match via calculateFitScore at send time.

Why: no throwaway-draft spam; no intros the matching engine wouldn't have shown. Depends on the price-bucket fix (54f7f61).

G5 Withdraw timing

Withdraw allowed only when status is pending and now − createdAt ≥ 24h. Enforced server-side; UI shows a countdown before that.

Why: agent gets a guaranteed day; withdraw can't be used for rapid-fire slot recycling.

G6 Structural (no payload to steal)

Because of the visibility rules (§2.2), an intro carries no contact info in either direction until money moves — spam wastes attention but leaks nothing.

Why: the visibility design itself is the last line of defense.

Spec 4 Boundaries
4.1 · Failure modes

Edge cases

Concurrency & integrity

  • Double-click send / two tabs → advisory lock + partial unique index; second attempt gets a clean "already requested" error.
  • Agent responds while client withdraws → first transaction wins; loser gets "no longer pending".
  • Duplicate/replayed webhooks → idempotent on stripePaymentIntentId; connecting already-connected rows is a no-op.
  • All timing checks (24h, 30d, window) use server time only.

Payment oddities

  • Webhook slower than redirect → success page polls ~30s, then "still processing, refresh shortly".
  • Checkout completed after guards changed (e.g. race where the only accepted intro got connected another way) → fulfill anyway; window is never lost money.
  • Window expires between agent's accept click and commit → whatever the transaction reads wins; both outcomes are valid states.

People change

  • Client edits preferences after sending → existing intros keep their snapshot-in-time validity; fit is only checked at send.
  • Agent deactivates/deletes account with intros outstanding → noted for the account-deletion feature to sweep intros to declined-equivalent.
  • User with both buyer and seller profiles → fully independent slots, caps, and windows per role.
